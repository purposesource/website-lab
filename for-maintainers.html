Adopt in five steps

The adoption routine, from the rights check to the badge. The pull request in step 3 is the only change to your repository, and you merge it yourself.

Free · no account or separate agreement needed to adopt · Updated 2026-10-28

  1. 1. Check who holds the rights

    Time: depends on the project

    Read the licence with your community. Check existing licences, contributor permissions and dependencies: you need sufficient rights in the work.

    Code your project includes under a share-alike (copyleft) licence is never switched automatically; changing it needs every contributor’s agreement.

    The full adoption guide⁠ (live site)

  2. 2. Choose the release boundary

    Time: one decision

    The licence applies to the new releases you choose. Releases already published keep their terms.

  3. 3. Open the adoption pull request

    Time: about a minute, once the rights are clear

    In the dashboard, “Adopt the licence” prepares a pull request under your own GitHub account. GitHub asks you once to authorise it, and the permission is removed when the work is done. You read the pull request and merge it yourself: nothing changes in your repository until you do.

    Pull request · sample-commons/purpose-cliSample

    Adopt the Purpose Source License
    Opened by the repository’s administrator, from the dashboard, under their own GitHub account.

    • LICENSEThe unchanged text of Purpose Source License 1.0. Required.
    • README.mdOptional: a small Purpose Source badge at the end.
    • PURPOSE.ymlOptional: the project’s settings file. Never legal terms.

    Check: LICENSE matches SHA-256 212c9280…0a87

    An MIT, Apache, BSD, ISC or zlib licence already in the repository is replaced, and its text is kept word for word in NOTICE. Any other licence is skipped, and nothing is written.

    Several repositories at once, and later licence updates, work the same way. If a pull request ever proposes a text other than the canonical one, do not merge it.

    The Association never opens a pull request on a repository that did not ask.

  4. 4. Merge, then add the badge

    Time: a few minutes

    Merge the pull request. The badge reads the public record, so it says what the registry says about your repository. Once the registry lists the repository, its page offers more badges and a project card.

    Add the GitHub topic purpose-source so people can find the project. [proposal from the study]

  5. 5. Tell people

    Time: a few minutes

    Your registry record shows the adoption date. A short text you can adapt:

    For your README or release notes [draft wording]

    From release [version], this project is licensed under the Purpose Source License 1.0. People and small organisations use it free; larger organisations take annual coverage, and the fees go, after published, capped costs, to listed charities. Each release becomes Apache-2.0 four years after its publication. https://purposesource.org/license

What the Association does for your project

It collects the fees through Paddle, our reseller, which handles tax and invoices. It records coverage, issues certificates, publishes the records, and passes the fees on, after published, capped costs, to listed charities. You build no billing and sign no contracts with buyers.

Afterwards

Add the repository in the dashboard if you want administrator powers, such as granting waivers. This is optional and separate from adoption: a registered repository is listed, with its own page and badge, whether or not anyone claims it.

You can leave at any time for future releases; earlier releases keep their terms.
